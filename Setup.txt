TestBuddy — Setup & Run Commands
================================

Prerequisites
-------------
- Node.js 20+
- PostgreSQL 18 (local)
  Database : testbuddy
  Username : admin
  Password : admin
  Host     : localhost
  Port     : 5432


1) Create PostgreSQL database (one-time)
---------------------------------------
Open psql as postgres, then run:

  CREATE ROLE admin LOGIN PASSWORD 'admin';
  CREATE DATABASE testbuddy OWNER admin;


2) Backend (Node.js / Express) — port 8080
------------------------------------------
cd backend
npm install
npm run dev

Health check: http://localhost:8080/api/health


3) Frontend (Vite React) — port 5173
------------------------------------
cd frontend
npm install
npm run dev

Open: http://localhost:5173


4) Extension (Tester-only) — optional
-------------------------------------
cd extension
npm install
npm run pack

Then either:
  - Download zip from http://localhost:5173/  (TestBuddy-extension.zip)
  - Or load unpacked folder: extension\dist

Chrome: chrome://extensions → Developer mode → Load unpacked
Select the unzipped "TestBuddy" folder (contains manifest.json).

IMPORTANT: Extension login accepts only role = TESTER.
Demo tester: alice@testbuddy.local / password


5) AI service (title / steps polish) — port 8001
------------------------------------------------
cd ai-service
python -m venv .venv
.\.venv\Scripts\activate
pip install -r requirements.txt

# Create .env (copy from .env.example) and set ONE key:
#   GROQ_API_KEY=...          (recommended, free: https://console.groq.com/keys)

uvicorn main:app --reload --port 8001

Health: http://localhost:8001/health

Also add to backend/.env:
  AI_SERVICE_URL=http://127.0.0.1:8001

Roles cheat-sheet
-----------------
- SuperAdmin : organizations, all users, hard-delete users; modules view-only (no add/edit/delete); creates users with auto-generated temporary passwords
- Manager : create projects under an org (capped by org maxProjects from SuperAdmin, and MAX_PROJECTS_PER_MANAGER); sees all org projects; modules; full bug edit; user CRUD; org members; assign Manager/Dev/Tester; grant project access; auto-generated temporary passwords for new users
- Tester : org member; sees only Manager-assigned projects; modules, create bugs (extension), comments, bug status
- Developer : org member; sees only Manager-assigned projects; comments + bug status only (no bug create / no project create / no modules manage)

Passwords
---------
- Admin-created users get an auto-generated 16-char temporary password, shown once in the Create user modal.
- On first login the user is sent to /change-password and cannot reach any other API until they set their own password.
- "Reset password" on a user row (Users page, or Settings -> Reset password) generates a new temporary password and re-forces the change.
- Admins can never type a password for someone else; PUT /api/users/:id rejects newPassword.
- Policy for user-chosen passwords: 10-128 chars, one lowercase, one uppercase, one number, one symbol, no spaces,
  no character repeated 3x in a row, not a common password, and not containing the user's name or email.
- Changing a password (or an admin reset) bumps users.password_changed_at, which revokes every token issued earlier.
  The change-password response returns a fresh token so the current tab stays signed in.
- Seeded demo accounts keep the literal password "password" because the seed writes the bcrypt hash directly;
  the policy only applies when a password is changed through the API.
- The two responses that carry a plaintext temporary password (POST /api/users and POST /api/users/:id/reset-password)
  are sent with Cache-Control: no-store.
- Both are also written to the audit log as one JSON line per event ({"type":"security","event":"password.admin_reset",...})
  recording actor, target, target role and IP. The password itself is never logged.

Project access: org membership alone is not enough for Tester/Developer — Manager must add them to each project.
Project create: Manager only (SuperAdmin also allowed); Developer/Tester cannot create. Managers are capped by the organization's project limit (SuperAdmin sets maxProjects) and by MAX_PROJECTS_PER_MANAGER (default 10).
